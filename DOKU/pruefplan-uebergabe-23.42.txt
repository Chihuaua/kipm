5. BEKANNTE FEHLER / ERFAHRUNGEN AUS DEM TEST (nicht erneut suchen!)
--------------------------------------------------------------------------
  [F1] Zombie-Helfer: Ein Helfer aus einem gelöschten/Mülleimer-Ordner hält Port 8790.
       Symptom: "bash start.sh" meldet "läuft bereits", Browser zeigt JSON
       {"ok": false, "out": "nicht gefunden: index.html"}.
       Diagnose: for p in $(pgrep -f projektmanager.py); do readlink /proc/$p/cwd; done
       Fix:      pkill -f projektmanager.py   (danach pgrep muss leer sein)
  [F2] Dateimanager benennt jede ZIP-Entpackung um ("… (1)", "… (59)" …) → viele
       Kopien, teils unvollständig. Lösung: NUR den einen Helfer-Ordner (Punkt 6) nutzen.
  [F3] git-ignorierte Dateien (z. B. .env*, *.bak) sind dem Geheimnis-Guard unsichtbar
       (by Design) — die .gitignore ist erste Linie, der Guard zweite Linie für
       git-SICHTBARE Dateien. Die GUI meldet ignorierte Dateien ehrlich mit Namen.
  [F4] Chat-Upload-Größen: lange check.sh-Ausgaben und Screenshots das Chat-Limit
       sprengen. Neue Sitzungen: nur kurze Textausgaben anfordern.
  [F5] "git status" zeigt ignorierte Dateien nur mit "--ignored" — der Helfer macht
       das seit 23.38 selbst (akt_offene_speichern).
  [F6] Beendigungsfenster-DESIGN (funktionell ist stop.sh einwandfrei, verifiziert am
       07.11.2026: Helfer wird sauber beendet, pgrep leer). Zenity 4.2.2 (GTK4) hat
       die --css-Option entfernt → Fallback auf schmales System-Fenster. FIX BEREITS
       IM PAKET: stop.sh bevorzugt jetzt kdialog (natives dunkles KDE-Fenster),
       zenity nur Fallback. Vom Besitzer vertagt ("Funktion vor Design") — anwenden:
       aktuelle stop.sh aus dem Paket/Vorschau-Ordner in den Helfer-Ordner kopieren,
       "bash stop.sh" testweise ausführen.
  [F7] SYSTEMREGEL (am 07.11.2026 live entdeckt, GH013): Das Repository erlaubt
       ÄNDERUNGEN AN MAIN NUR PER PULL REQUEST — direkte "git push origin main"
       werden abgelehnt. Deshalb arbeitet der Helper ("Patch zu GitHub") immer mit
       Zweig + PR, und der Besitzer muss Korrekturen an main ebenfalls per PR fahren.
       Lokale Commits auf main dürfen zwar gebaut werden, sind aber bis zum Merge
       eines PRs nicht auf GitHub.
  [F8] WORKFLOW-MERKSÄTZE (aus dem N3-Volltest):
       a) Im PR-Fenster: Test-PRs per "Close" beenden — "Merge" nimmt sie endgültig
          nach main. Korrekturen/Reverts dagegen WERDEN gemerged.
       b) Zweige (lokal UND remote) erst löschen, NACHDEM auf GitHub "Merged"
          steht — sonst wird die PR nicht mehr mergbar.
       c) Revert eines Merge-Commits: "git revert --no-edit -m 1 <Merge-Hash>"
          (--no-edit vermeiden, sonst öffnet sich der Editor).
